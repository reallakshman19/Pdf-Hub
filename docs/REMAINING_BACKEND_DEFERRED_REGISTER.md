# Deferred Backend Features Register

This document lists server‑side features that have been deliberately deferred from the initial front‑end‑only implementation of DocCraft.  Each entry below includes a brief description of the capability, why it has been postponed, what client‑side fallback (if any) exists, and the conditions under which it should be enabled in the future.

| Feature | Reason for Deferral | Client‑Side Fallback | Activation Condition | Notes |
| --- | --- | --- | --- | --- |
| **Server OCR** | The initial release operates entirely in the browser without a back‑end. Running OCR on the server requires PyMuPDF and a job queue, which are not included. | Tesseract.js preview OCR runs in a Web Worker. | Once a FastAPI service with OCR endpoints and job management is deployed. | When enabled, the front‑end should detect `serverOcrAvailable=true` in capabilities. |
| **WebSocket OCR Progress** | Requires a persistent server connection to stream per‑page status updates. Without a server there is no WebSocket channel. | Progress is polled from the local job store. | When a WebSocket endpoint `/api/ocr_ws` becomes available. | The UI must handle reconnection and partial results. |
| **PyMuPDF Page Rewrite** | Full page extraction, rotation and insertion rely on server‑side libraries. The preview release can only plan operations; it cannot mutate PDF bytes outside of pdf‑lib’s limited scope. | Client‑side compose functions can flatten overlays and annotations but cannot perform secure redaction or reflow pages. | When `pdf_engine` exists in the back‑end. | Ensure that only safe operations are exposed to the UI until this feature is available. |
| **Secure Final Redaction** | Removing underlying content (text, images, annotations, OCR text) requires destructive PDF rewriting. This is not possible in the browser alone. | A redaction preview tool allows users to mark regions and export JSON plans. | When a vetted redaction pipeline is implemented on the server. | The UI should clearly label redaction as preview‑only until this is enabled. |
| **Large PDF Range Service** | Streaming pages from large documents via HTTP range requests demands a server. | The front‑end loads complete ArrayBuffers; performance may degrade for very large files. | When a document storage service exposes range‑enabled endpoints. | The viewer should automatically switch to range mode when available. |
| **Server Macro Jobs** | Executing macros that involve heavy operations (such as batch OCR or merging many PDFs) requires server resources. | Macros are limited to safe client‑side operations and command plans. | When macro endpoints exist on the server. | Macro commands must still go through the command dispatcher for undo/redo and auditing. |
| **SQLite Annotation Store** | Persisting annotations across devices requires a server database. The preview release stores annotations in IndexedDB only. | Local IndexedDB storage. | When annotation APIs (`/api/annotations/{documentKey}`) are available. | Ensure that migrating local annotations to the server is seamless. |
| **Server‑side Merge/Split for Large Files** | Splitting or merging large PDFs in the browser can exhaust memory. These operations are better suited to a back‑end. | The UI presents operation plans and warns about limits. | When the `pdf_engine` exposes merge and split endpoints. | Client code should detect `serverAvailable` before enabling large file operations. |
| **Server‑side OCR Checkpointing** | For long documents, saving intermediate OCR results to persistent storage allows for resuming jobs. This requires a back‑end. | None; client OCR jobs must complete in one session. | When job checkpoint APIs exist. | The front‑end should handle resuming jobs when a jobId is provided via URL. |

Until these features are enabled, the UI must honestly disable or hide the corresponding controls and provide clear messaging to users about their unavailability.
